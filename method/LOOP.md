# 多代理寫作流程

**v2.2｜2026-11-09**（v2 當天加入出題者、構想去重與第一直覺清單；v2.2 加入替代方案複查、任務卡不寫衝突）。分三級，預設用「標準」。v1.1 的逐段循環保留為「完整」級。整套流程的來源有兩個：AI_Novel_Portable_Kit 的「3 寫手競稿＋3 讀者盲審投票」（品川五輪，見 `examples/loop_benchmark_shinagawa.md`），以及〈零夜｜無脈〉的「專科審稿＋獨立驗收」。每次實測的數字與修訂依據在 `method/iteration_log.md`。

寫作標準一律看 `WRITING_GUIDE.md`；這份文件只管分工、順序、把關與用量。

## 三個等級

| 等級 | 什麼時候用 | 做法 | 用量（一篇 18,000 字） |
|---|---|---|---|
| **輕量** | 只有單一對話視窗；短篇、小品、改寫 | 沒給方向時，先自己出題、把任務卡交給 Charles 審。單稿：照 `WRITING_GUIDE.md` 動筆流程寫，完成後在幕後依 `method/reader_prompt.md`「標準級 E」的五項與共同部分的「一票否決」自審（單稿，不比較、不投票），修完才交 | 估計 20–30 萬 token |
| **標準**（預設） | Charles 要完整一篇、說「多代理」「競稿」「分工」，而且環境有子代理工具 | （沒給方向時：出題者出任務卡 → Charles 審）→ 設定摘錄包 → 攪局 → 3 寫手先交構想、去重，再寫完整一篇 → 編輯兼正典＋冷讀者盲審 → 勝出的寫手自己修 → 改動超過 5% 就複審 | 實測約 106–129 萬（〈回條〉12,400 字約 106 萬；〈第二號窗口〉14,000 字含出題者約 129 萬） |
| **完整** | 高解析度連載、一段一段寫，Charles 指定要逐段競稿 | v1.1 逐段循環：每 3,000 字 3 寫手＋3 讀者 | 實測約每段 100 萬，一篇 18,000 字約 600 萬 |

小修、改幾句、回答設定問題，不開任何流程。

## 角色

- **主控**（接到任務的 Claude）：寫任務卡、做設定摘錄包、分派、匿名化、計票、整理必改清單、量改動、入庫、記錄。**主控不替寫手構思劇情，也不自己改稿。**新東京第二輪，主控照讀者意見改的句子裡就有兩處引入新錯。
- **出題者**：提示詞在 `method/proposer_prompt.md`。Charles 沒給方向時，由他想點子、寫任務卡草稿；任務卡審定後，再替三位寫手各出一句攪局。他只讀任務卡、世界觀、正典的核心章節和 `method/idea_log.md`；出題階段實測約 12.7 萬 token（〈第二號窗口〉，不含攪局）。
- **寫手 ×3**：提示詞在 `method/writer_prompt.md`。
- **讀者**：提示詞在 `method/reader_prompt.md`。
  - **E 編輯兼正典**（標準級）：讀完整正典、世界觀、本篇用到的 world 檔與 `WRITING_GUIDE.md`。同時負責 v1.1 R1 的文風與骨架清單，以及 R2 的正典、連續性與動作物理清單。全流程只有這一位讀完整正典，是摘錄包的安全網。
  - **C 冷讀者**：不讀任何設定與指南，只讀三篇稿；續寫時再加上前一段定稿。負責好不好看、讀不讀得懂、想不想往下讀，是抗討好的主力。用主模型：換小模型的對照實測沒有省到用量，投票也不同（`method/iteration_log.md` 2.3）。
  - 完整級仍用 v1.1 的 R1／R2／R3 三位讀者。
- **複審者**：沒讀過這篇任何版本。只在改動超過 5% 時出場。

## 標準級流程

工作檔放在 `workshop/<YYYYMMDD>_<題目>/`：

```
proposal.md       出題者的 3 個點子與任務卡草稿（Charles 沒給方向時）
brief.md          審定的任務卡：情境、篇幅、時期、限制、不可動的設定（不寫情節）
provocations.md   出題者給三位寫手的攪局
concept_A.md …    寫手構想與第一直覺清單
pack_spec.txt     摘錄範圍；context_pack_1.md … 設定摘錄包（原文摘錄，標明出處與行號）
draft_A.md …      寫手原稿；notes_A.md … 寫手附註（只給主控）
mapping_PRIVATE.md  匿名對照
candidates/稿件1.md …  匿名稿；verify.txt 檢查腳本結果
reviews/E.md、reviews/C.md
tally.md          計票、裁決、必改清單、改動量、複審結果、用量
final.md          定稿
```

0. **選題**
   - Charles 給了方向：主控照方向寫 `brief.md`。
   - Charles 沒給方向（例如「寫一篇」「隨便寫」）：派出題者讀 `method/idea_log.md` 等資料，想 3 個點子，推薦一個並寫成任務卡草稿（`proposal.md`）。
   - **任務卡一律先交 Charles 審。**他可以直接通過、修改、換成另一個點子，或叫出題者重出。審定的版本存成 `brief.md`，才進入下一步。在沒人能審的排程或無人值守情境裡，主控照推薦點子開工，並在回報開頭寫明任務卡未經審核。
1. **準備**
   - `brief.md`：只寫情境、各方欲望與限制，**不寫該發生什麼情節，也不寫張力在誰與誰之間、是什麼衝突**（〈同桌出境〉的任務卡寫了「雪奈最順手的愛法正好拿走琉璃要的東西」，三篇的骨架就全部長成同一條）。主控補限制時，只寫要處理的問題，不暗示處理方式，也不要把人物或場景排成順序清單。〈銀色幽靈傳說〉的任務卡把受訪者依序寫成「銜尾蛇、真希、奏、神諭」，三篇裡就有兩篇照這個順序走成同一條訪談鏈。篇幅寫成「目標 N 字，不得少於 M」；只給區間的話，三位寫手都會停在下限附近。
   - 設定摘錄包：主控讀完整正典與相關 world 檔，把範圍寫成 `pack_spec.txt`，再跑 `python3 method/build_context_pack.py <spec> <工作資料夾>`。腳本照行號**原文摘錄**，不摘要、不改寫，每段標明來源檔與行號，並自動切成每份不超過 4 萬 bytes 的 `context_pack_1.md`、`context_pack_2.md`……，避免超過單次讀取上限。固定收錄正典第 0–4 章（不可變核心、外觀、人格、對話）與第 19–20 章（故事生成原理、一句話版本）。其餘依本篇需要加入：用到的身分章（6 銀色幽靈／7 零夜）、戰力（8–9）、裝備（13／14）、關係（18 對應人物）、世界觀相關節，以及出場人物、組織、地點檔的相關節。長度目標是正典全文的五到七成。
   - **攪局**：任務卡審定後，出題者替三位寫手各出一句攪局（`provocations.md`）。三句要在結構、張力來源與雪奈的位置上明顯錯開；只出方向，不出情節與道具。攪局取代由主控指定的因果變數與切入角。
2. **寫作**：三位寫手同時開工，各寫**完整一篇**，分兩階段：
   - **先交構想**：讀完設定後先停下，交約 200 字的構想（各方欲望、骨架、開場與結尾畫面）、5 個關鍵細節，以及自己換掉的第一直覺清單。主控把三份構想並排，撞到的骨架、場景、道具或台詞，用接續訊息逐一退回：「你和另一位都用 X，換掉」。不撞就回「通過」。主控只比對、不出點子。**被退回的寫手先交替代方案（構想檔末尾一行「換掉：…→改為：…」）就停下**；主控把所有替代方案和其他人的構想並排再比一次，確認沒撞才放行全文。〈同桌出境〉實測，兩位寫手被要求換掉同一個元素後，各自想到同一個替代品。
   - **再寫全文**：通過後，同一位寫手接著寫全文，不必重讀設定。
   - 沒有出題者時（例如 Charles 已給很具體的方向、不想多一個角色），改用**骨架分流**：每人分到 `WRITING_GUIDE.md` 因果表的一列，寫成違反第一直覺的選擇；要分開場景時再加切入角（生活與人際／空間與現場／物證與制度）。
   - **第一直覺清單**：三位寫手是同一個模型，連順手想到的道具、場所與台詞都會一樣。〈銀色幽靈傳說〉三篇各自想出了同樣的蒙布朗配糖漬栗子、灰色大帽 T、凌晨的投幣洗衣店，連奏的台詞都一字不差，而這些都不在摘錄包裡。所以寫手動筆前，要先在附註列出自己最先想到的 5–8 個具體細節（甜點、衣著、場所、店內陳設、關鍵台詞），正文一律換掉。
   - **批次讀檔**：第一次工具呼叫就把摘錄包、`WRITING_GUIDE.md`、任務卡一次平行讀完；正文用一次寫檔完成；跑一次檢查腳本、修掉硬傷。讀檔與寫檔照這個方式批次完成，因為每多呼叫一次，前面讀過的內容就要整份重送一次；修硬傷、讀包外原檔與照必改清單修訂不受此限。
   - 寫手覺得摘錄包不夠時，可以自己讀原檔，但要在附註寫明讀了什麼、為什麼。這是用來修正摘錄包範圍的訊號。
3. **匿名化**：三篇改名 `稿件1–3`，順序打亂；跑 `python3 method/verify_prose.py`，結果附給 E。
4. **盲審**：E 與 C 同時開工，各自逐篇挑刺、引原文、投唯一一票，並列出勝出稿的必改清單。
5. **裁決**
   - 兩人同票，就是勝出稿。
   - 兩人不同票時：E 的票如果是因為對方的稿有無法小修的一票否決（OOC、正典硬傷、時序穿幫），聽 E；否則聽 C。
   - 兩人都判定三篇骨架失敗，作廢重跑，主控改的是 brief，不是字。
6. **修訂**：主控把兩位讀者的必改合併成一張清單，衝突時依專長裁決（閱讀體驗聽 C；正典、物理、醫療、文句、骨架聽 E），再用接續訊息交給**勝出的那位寫手**修改，寫手對自己的空間配置與伏筆最清楚。改完由主控用 `difflib.SequenceMatcher` 量改動字元數。
   - 5% 以內：主控逐條核對清單都改到了，入庫。
   - 超過 5%：送複審（`reader_prompt.md` 複審版）。不通過時，把複審者逐句指定的改法交回寫手照改；之後主控若還有一兩句要動，要在 tally 和回報裡標明「未經複審」。
   - **不從落選稿拼接場景。**
7. **入庫**：定稿存到 `stories/<題目>.md`，開頭列出本篇新創、不升格正典的元素。tally 記下每個代理的 token 用量。把這篇的題目核心、三句攪局，以及讀者指出的新慣性元素補進 `method/idea_log.md`。

## 完整級流程（v1.1 逐段循環）

和標準級的差別：
- 每段約 3,000 字，每段都由 3 寫手競稿。寫手讀完整正典，或讀摘錄包加前一段定稿，由主控視成本決定。
- 讀者用 R1 文風編輯、R2 正典與連續性、R3 冷讀者三位。1:1:1 時，先排除帶著無法小修的硬傷的稿，再取 R3 的票。
- 續寫要附 `ledger.md`（前文對帳表：時間、星期、地點、在場人物、傷勢、裝備、手上物件、約定、未兌現伏筆）；更早的段落濃縮成 `summary.md`。冷讀者讀上一段定稿全文。
- 三篇撞同一個開場時，下一輪改給不同的物理起點。
- 驗證紀錄見 iteration_log 2.1、2.2（〈新東京遊蕩〉一、二）。

## 共通規則

- **藏設定是優點，秀設定是缺點**，讀者以此為立場；好看是最高標準，「錯最少」不能單獨勝出。
- 新創的人物、組織、場所與物件只屬於該篇，不升格正典。
- 交給 Charles 的是正文。審稿、計票與工作筆記留在 `workshop/`，他要看再給。回報時用一兩句說明怎麼選出來的、修了什麼、有沒有未經複審的句子。

## 常見問題

- **三篇撞車**：標準級在構想階段去重（第 2 步）；兩位讀者都判定骨架相同，就回頭改任務卡（第 5 步）。用骨架分流或跑完整級時：場景撞，就加切入角或不同的物理起點；戲劇功能撞，就換分配的因果變數列。不要規定劇情。
- **讀者找不到問題**：照模板寫了「未發現」並說明檢查過什麼，就接受。整份審稿只有稱讚、沒有引文，才是討好症：要求讀者先列出「這篇最可能被罵的三個地方」並引原文。
- **寫手照抄摘錄包的形容詞**：這是熟人盤點的變形。E 抓到就列入必改；反覆出現時，在 brief 提醒「摘錄包是用來校準的，不是素材庫」。
